## 2025-03-17 - PowerShell Command and Script Injection
**Vulnerability:** The application was passing dynamic PowerShell commands to `powershell.exe` by constructing the `-Command` string using string interpolation. It was also embedding unsanitized user inputs (`vmName` and OS-retrieved `vhdxPath`) into these PowerShell scripts wrapped in single quotes (`'`). Both practices allowed for arbitrary PowerShell code injection if the strings contained `"` or `'`.
**Learning:** Using `Arguments = $"-Command \"{command}\""` for `ProcessStartInfo` is unsafe and susceptible to injection via double quotes. Embedding string variables inside PowerShell scripts surrounded by single quotes is also unsafe if the variables contain a single quote, which breaks out of the string context.
**Prevention:** Always use `ProcessStartInfo.ArgumentList` to securely pass command-line arguments to processes like `powershell.exe`. When dynamically embedding strings into a PowerShell script wrapped in single quotes, always escape the input by doubling single quotes (`input.Replace("'", "''")`).
## 2024-05-18 - Prevent PowerShell Command Injection via `ProcessStartInfo.EnvironmentVariables`
**Vulnerability:** Untrusted external input (like Hyper-V virtual machine names from `Get-VM` and WMI query results like `Win32_VideoController`'s `Name`) was directly interpolated into PowerShell script strings using C# interpolated strings (`$"{var}"`) inside `RunPowerShellCommand`. A malicious VM name containing single quotes or semicolons could break out of the single-quoted string context and execute arbitrary PowerShell commands on the host machine. The previous "fix" of `vmName.Replace("'", "''")` was insufficient as it relies on character escaping rather than structural separation.
**Learning:** Interpolating user input or data from external sources (even local ones like WMI) directly into executable shell commands is a command injection vulnerability. When executing `powershell.exe -Command`, positional `ArgumentList` arguments and string interpolation are re-parsed by the shell, meaning characters like `;`, `$`, or `&` can alter the command logic if not properly escaped.
**Prevention:** To securely pass parameters to PowerShell scripts invoked via `Process.Start` without relying on string manipulation or escaping, set `UseShellExecute = false`, pass the untrusted data as environment variables via `ProcessStartInfo.EnvironmentVariables`, and reference those variables within the PowerShell script block using the `$env:VARNAME` syntax.
